# 后端开发约束（逐条执行，无例外）

技术栈：Spring Boot 3.3.x + JDK 17 + MyBatis-Plus 3.5.x + MySQL 8.x + Redis 7.x + Baomidou Dynamic-Datasource 4.x + Spring Security + JWT (jjwt) + Caffeine + Spring WebSocket + JimuReport + EasyExcel + Maven


# 一、P0 性能（违反 = 生产事故）

## 数据库

1. 禁止循环单次查库，关联数据必须用 MyBatis-Plus 的 selectBatchIds 或 selectList 传入 ID 集合一次性批量查询。任何在 forEach 或 for 循环内部调用 Mapper 方法的行为都禁止。

2. 百万级数据必须分页查询，使用 MyBatis-Plus 的 Page 对象配合分页拦截器，禁止把全量数据加载到内存中再手动分页。分页查询必须同时指定排序字段，避免 MySQL 随机排序导致分页结果不一致。

3. 禁止 N+1 查询：当一个循环中需要关联查询另一个表的数据时，必须先收集所有 ID 用 stream 的 map 操作提取为一组集合，然后一次性调用 selectBatchIds 批量查询，将查询结果转为 Map 结构按 ID 获取，禁止每条记录单独调一次 Mapper。

4. 所有作为 WHERE 条件、JOIN 关联、ORDER BY 排序的字段必须建立数据库索引。上线前用 EXPLAIN 分析 SQL 执行计划，检查 type 列是否为 ALL（全表扫描），如果出现 ALL 级别必须加索引优化或重写查询逻辑。

5. 列表查询如果需要关联多张表的数据，禁止直接使用联表 SQL 再分页（会导致 COUNT 不准、分页数据重复），必须改为先查主表 ID 的分页结果，再用这个 ID 列表去关联查询其他表的数据填充。

6. 使用 Baomidou Dynamic-Datasource 多数据源时，在 Service 方法上通过 @DS 注解指定数据源。注意 @DS 注解不能和 @Transactional 嵌套导致数据源切换失效，如果方法同时需要事务和指定数据源，主数据源上的事务加上 @DSTransactional 注解。

7. 读写分离场景下，查询方法使用 @DS("slave") 走从库，写方法走默认主库，避免所有流量都打到主库。但从库可能存在同步延迟，写后立即读的关键业务必须强制走主库。

## 缓存

8. 热点基础数据（物料分类、AQL 配置、字典数据）走 Caffeine 本地缓存，设置合理的最大条目数、过期时间和自动刷新策略。动态业务数据（库存、订单、审批流）走 Redis，所有缓存 Key 统一管理在常量类中，禁止在代码里直接写死 Key 字符串。

9. Redis 中所有缓存 Key 必须设置过期时间，禁止无 TTL 的永久缓存，防止内存被打满。过期时间根据数据变更频率设定：基础数据缓存可以设置较长时间如 30 分钟到 2 小时，实时性要求高的数据设置 5 到 15 分钟。

10. 写操作（新增、修改、删除）后必须同步清除相关的 Caffeine 和 Redis 两级缓存。清除顺序采用 Cache-Aside 模式：先清除缓存，再写入数据库，而不是先写库再清缓存，避免并发读写时缓存回源写入脏数据。

11. 缓存穿透防护：对于数据库中不存在的数据，在 Redis 中缓存一个空值标记，设置较短的过期时间（建议 30 到 60 秒），防止恶意请求反复穿透缓存打到数据库。高频查询场景可配合布隆过滤器。缓存击穿防护：对于热点 Key，在缓存失效时加分布式互斥锁，只让一个线程去查库重建缓存，其他线程等待并复用重建结果。缓存雪崩防护：所有缓存的过期时间加上一个随机偏移量（建议 5% 到 15%），避免大量 Key 同时过期造成数据库瞬时压力。

## 异步与资源

12. 发邮件、短信、站内通知、WebSocket 消息推送、Excel 导出、JimuReport 报表生成等耗时 IO 操作，禁止在 Controller 的主线程中同步执行阻塞请求响应。必须使用 Spring @Async 异步方法或 Spring Event 事件机制解耦，将响应快速返回给前端，后台异步执行耗时操作。

13. 接口响应时间超过 500 毫秒的场景必须考虑异步化或引入消息队列削峰。如果暂时无法异步化，至少要在 Controller 层加上超时控制，避免单个慢请求拖垮整个线程池。

14. 数据库连接池不发送一次性超大 SQL。MyBatis-Plus 的 saveBatch 和 updateBatch 方法单次提交最多 1000 条记录，超过这个数量必须循环分批提交，每批之间适时让出连接资源。

15. 大批量数据导出 Excel 时，使用 EasyExcel 的流式写入模式，禁止一次性把全部数据加载到内存再生成 Excel。通过分批查询数据库（每批 1000 到 5000 条）配合 EasyExcel 的 write 方法逐批写入文件。

## 并发

16. 库存扣减、余额变动等涉及数量增减的接口，必须使用 Redis 分布式锁加 Lua 脚本实现原子操作。Redis 分布式锁使用 SET NX EX 命令实现，设置合理的锁超时时间，释放锁时用 Lua 脚本校验锁的持有者再删除，防止误删其他线程的锁。单机环境下用 Caffeine 本地锁作为 Redis 不可用时的降级兜底。

17. 高频并发更新的字段（版本号、状态流转、计数器）必须加上乐观锁版本号字段，用 MyBatis-Plus 的 @Version 注解自动处理。更新时 WHERE 条件带版本号，更新失败说明有其他线程已经修改，业务层需要捕获并重试或提示用户。

18. 读多写少的场景使用 ReentrantReadWriteLock 读写锁或用 CopyOnWrite 并发集合，读操作不加锁或用共享锁，写操作加排他锁。禁止在锁持有期间（synchronized 块或 Lock 内部）执行查库、调 RPC、读写文件等 IO 操作，防止锁持有时间过长。

19. 使用 Spring WebSocket 进行实时推送时，必须控制单条消息的大小上限，禁止推送超过 64KB 的大消息。高频推送场景要做消息合并和节流，避免短时间内大量 WebSocket 消息冲刷客户端和服务器。


# 二、P0 Bug 预防（违反 = 线上故障）

## 数据正确性

20. 所有金额、数量、折扣率、税率等数值字段全部使用 BigDecimal 类型。BigDecimal 构造时必须使用字符串参数 new BigDecimal("0.1")，禁止使用 double 参数 new BigDecimal(0.1)，因为 double 类型的 0.1 在二进制中是一个无限循环小数，传入 BigDecimal 构造器时仍保留这个近似误差，金额计算会随时间累积产生漂移。

21. 加减乘除运算统一保留 2 位小数，使用 divide 方法时必须同时指定精度和舍入模式 RoundingMode.HALF_UP（四舍五入），禁止使用不指定精度的除法方法，因为遇到无限小数时会抛出 ArithmeticException。

22. 所有除法运算前必须判断除数是否为零。取余和取模运算前同样判非零。在涉及到用户输入的除数场景中，这个检查必须在最前面执行。

23. 库存数量、余额、积分等数量型字段，每次变动前进行三重前置校验：扣减前校验剩余值大于等于扣减值，增加前校验增加量大于零，数据库操作后校验最终结果不小于零。任意一个校验失败都要抛出明确的业务异常并回滚事务。

24. 订单号、合同号、手机号、物料编码等唯一业务键，数据库层面必须建立唯一索引作为兜底约束。代码层面在插入数据前先查一次是否存在，防止依赖数据库唯一索引抛异常来拦截（用户体验差）。同时插入操作仍然用 try-catch 捕获 DuplicateKeyException，防止极端并发情况下查出来不存在但插入时已被其他线程占用的情况，捕获后返回明确的中文业务提示，不抛原生英文异常给前端。

25. Spring Security 集成 JWT 认证时，密码必须使用 BCryptPasswordEncoder 加密存储，禁止明文或简单 MD5 存储。JWT Token 的签名密钥从环境变量读取，禁止硬编码在代码中。Token 过期时间根据业务场景设置：Access Token 建议 30 分钟到 2 小时，Refresh Token 建议 7 天。Refresh Token 需要使用 Redis 存储并验证其有效期，支持主动失效。

26. JWT Token 的签发和刷新逻辑中，禁止在 Token Payload 中存放密码、手机号、身份证等敏感信息，PayLoad 是 Base64 编码非加密，任何人都可以解码查看内容。仅存放用户 ID、用户名、角色标识等非敏感信息。

27. Caffeine 本地缓存用于存储已签发但未过期的 JWT Token 白名单或已注销的 Token 黑名单时，必须设置最大条目数上限和过期时间与 Token 剩余有效期一致，防止内存溢出。

## 空值与边界

28. 方法返回值是集合或数组类型时，空值统一返回空集合 Collections.emptyList() 或 Collections.emptyMap()，禁止返回 null。调用方不需要判断 null，直接遍历空集合不会抛异常。

29. 字符串判空统一使用 Hutool 的 StrUtil.isBlank() 方法，它同时覆盖 null、空字符串和全空格字符串三种情况。数值类型判空使用 JDK 自带的 Optional 包装，禁止用等于 null 的裸判断。

30. 所有分页参数的 Controller 入参前置校验：pageNum 小于 1 时强制置为 1，pageSize 大于 200 时强制置为 200。这个校验必须在 Controller 层就完成，不能依赖 Service 层或者 MyBatis-Plus 分页拦截器的默认行为。

31. 所有 Controller 接口的入参 DTO 必须启用 JSR380 参数校验注解，包括 @NotNull、@NotBlank、@NotEmpty、@Min、@Max、@Pattern、@Email 等。嵌套对象属性用 @Valid 注解开启级联校验。List 类型的参数如果包含需要校验的元素，封装一个包装类加上 @Valid 注解。校验不通过时由全局异常处理器捕获 MethodArgumentNotValidException 和 BindException，返回格式化的校验失败信息。

32. 所有来自外部的输入数据都不可信任，必须做合法性和边界校验。外部输入包括：前端请求参数、文件上传内容、消息队列消费的消息、第三方回调（如 e签宝回调）的参数、JimuReport 报表的查询参数。

## 异常与日志

33. 全局异常处理器使用 Spring 的 @RestControllerAdvice 注解统一拦截。所有异常包装为统一的 Result 返回体，包含 code（整型错误码）、msg（字符串提示信息）、data（数据载体）。禁止原生异常堆栈和完整 Exception 信息直接返回给前端。

34. 业务异常定义枚举错误码体系，一个异常码对应一种明确的业务语义。例如订单不存在对应错误码 30001 和提示"订单不存在"，库存不足对应 30002 和提示"库存不足"。枚举中统一管理 code 和 message，禁止在各处业务代码中直接 new RuntimeException("xxx") 的方式抛异常。

35. 核心操作必须打印 INFO 级别日志，核心操作包括：新增单据、修改单据、删除单据、审批通过或驳回、库存数量变动（入库出库调拨）、支付和退款、以及与第三方系统（e签宝）的交互。日志中必须包含操作人 ID 或用户名、操作数据的唯一标识（订单号或 ID）、操作前后的关键值对比。

36. 禁止在 catch 块中只打日志不处理也不重新抛出异常。禁止使用 catch (Exception e) 这种笼统捕获的方式，必须捕获具体的异常类型。如果确实需要兜底，在最外层统一异常处理器中捕获 Exception。

37. 日志输出使用 SLF4J 的占位符格式：log.info("订单{}已创建，操作人{}", orderId, userId)，禁止使用字符串拼接方式：log.info("订单" + orderId + "已创建")，字符串拼接会在日志级别关闭时仍然执行拼接操作产生不必要的性能开销。

38. 日志禁止打印完整的手机号、身份证号、密码、密钥、Token、电子签合同内容。必须在日志输出前对敏感部分做脱敏处理，仅保留部分可辨识信息用于排查问题。

## 幂等与防重

39. 支付、扣款、库存扣减、订单创建等核心写接口，前端请求必须携带唯一的幂等键（使用业务流水号或全局唯一 TraceId），服务端通过两张方式双重防重：Redis 存储幂等键做快速去重，数据库去重表做持久化兜底。先查 Redis 是否存在，不存在则写入 Redis 并执行业务逻辑，业务操作完成后写入去重表。如果 Redis 中已存在则直接返回"请勿重复提交"。

40. 表单重复提交防控：前端生成一个一次性的防重 Token，服务端将该 Token 存入 Redis 并返回给前端。提交表单时前端将 Token 一并提交，服务端从 Redis 中校验并删除该 Token，如果 Token 不存在或已使用说明是重复提交。这种模式用于新增单据表单、付款申请单等场景。

41. 消息队列的消费者必须做幂等处理，基于消息的唯一消息 ID 或业务主键在消费前查去重表判断是否已消费过。因为 MQ 在异常重试场景下可能投递重复消息，消费者不幂等会导致数据重复处理。

## 并发数据安全

42. 状态流转必须校验前置状态：订单已取消的状态下禁止再发起支付，已发货的订单禁止修改收货地址，已入库的单据禁止重复入库。状态校验逻辑放在 Service 层方法的最前面，校验不通过直接抛业务异常。

43. 先查后改的模式（先 SELECT 查询一条数据，再基于查询结果 UPDATE）在并发环境下极易出现数据被覆盖的问题。这种场景必须加乐观锁（版本号字段 + @Version）或悲观锁（SELECT FOR UPDATE），最简单的方案是让 UPDATE 语句的 WHERE 条件带上版本号，更新返回影响行数为 0 则说明已被其他线程修改。

44. @Transactional 事务注解只用于多表联动、数据一致性要求高的场景，如：入库单创建同时增加库存、出库单创建同时扣减库存、采购结算同时更新采购单状态和财务数据。事务边界要尽可能小，只包裹必须联动修改的数据库操作。禁止在事务内部调用第三方接口（如 e签宝 API）、发送消息队列消息、写文件等操作，这些操作如果放在事务内会导致事务持有时间过长。如果需要保证外部操作和数据库操作的最终一致性，使用本地消息表或事务消息模式。

45. 使用 Dynamic-Datasource 多数据源时注意：@Transactional 默认只在主数据源上开启事务，不会跨数据源生效。如果需要操作多个数据源且保证一致性，使用 Seata 分布式事务或用补偿机制实现最终一致性，禁止在一个方法内对不同数据源分别加 @Transactional 期望自动生效。

## 安全（补充）

46. Spring Security 配置中关闭 Session 创建，使用无状态会话管理（SessionCreationPolicy.STATELESS），因为 JWT 本身就是无状态的认证机制。禁用 CSRF 保护，前后端分离架构不依赖 Cookie 传递认证信息，不需要 CSRF Token。

47. 方法级别的权限控制使用 @PreAuthorize 注解，在 Service 层方法上声明需要的权限标识或角色，配合 SpEL 表达式做细粒度校验。禁止在 Controller 层用 if-else 判断角色或权限，必须用 Spring Security 的注解声明式管理。

48. e签宝等第三方 API 的 AppKey、AppSecret、Callback 地址等配置走环境变量或配置中心，禁止硬编码在 properties 或 yaml 文件中。调用第三方接口必须设置合理的连接超时和读取超时时间（建议分别为 5 秒和 15 秒），超时后必须有重试机制（最多重试 3 次，间隔递增），重试仍失败时记录告警日志并返回明确的业务提示给用户。

49. e签宝的回调接口需要验证请求来源的合法性（验签），防止被伪造回调数据。验签逻辑放在拦截器或 AOP 切面中统一处理，不分散到各个业务回调方法中。

50. JimuReport 报表引擎的 SQL 查询必须走参数绑定，禁止前端传入的报表参数直接拼接到 SQL 中形成注入风险。报表访问需要做权限校验，不同角色的用户只能查看和操作自己权限范围内的报表和数据源。


# 三、P1 开发规范（违反 = 代码腐化）

## 分层

51. Controller 层只做三件事：接收并校验请求参数（通过 JSR380 注解自动校验）、调用 Service 层方法、将 Service 返回的结果包装为 Result 封装体返回给前端。Controller 层禁止写任何业务判断逻辑、SQL 拼接、循环计算、缓存操作。

52. Service 层分接口和实现类两层：Service 接口定义方法签名并标注业务语义，ServiceImpl 实现类编写具体业务逻辑。Controller 禁止直接注入和调用 Mapper，必须通过 Service 层间接访问数据库。

53. Mapper 层继承 MyBatis-Plus 的 BaseMapper，只负责数据库的增删改查操作。Mapper 中禁止添加缓存注解、业务判断、数据转换逻辑。如果需要复杂 SQL，使用 XML 映射文件或 LambdaQueryWrapper 条件构造器，禁止字符串拼接 SQL。

## 模型分离

54. Entity 实体类只做数据库表字段的映射，使用 MyBatis-Plus 的 @TableName、@TableId、@TableField、@TableLogic、@Version 等注解标注映射关系。Entity 中除了 getter 和 setter 方法外禁止包含业务方法。

55. 前端请求的参数使用 DTO 类接收，DTO 中的字段加上 JSR380 校验注解（@NotNull、@NotBlank 等）和 Swagger 文档注解（如果项目使用）。返回给前端的数据使用 VO 类包装，VO 中加上 Jackson 序列化注解做字段脱敏和格式化。禁止把 Entity 直接作为 Controller 的入参或返回值暴露给前端。

56. 禁止在 Controller 和 Service 之间使用 Map、JSONObject、JsonNode 等泛化类型传参，必须使用明确定义字段的 DTO 或 VO 类，保证类型安全和方法签名的可读性。

## 代码质量

57. 所有状态码、业务标识、缓存 Key 前缀、固定配置值必须抽取到常量类中集中管理，禁止在业务代码中直接写数字或字符串的魔法值。例如订单状态用枚举 OrderStatusEnum.PENDING_APPROVAL 而非数字 1。

58. if-else 嵌套层级不得超过 3 层。多层判断用卫语句提前 return 出不符合的条件，或用策略模式结合 Map 分发替代多个 if-else 分支，或用枚举内部实现多态行为。

59. 单个方法不超过 50 行，单个类不超过 500 行，方法参数不超过 5 个。超过限制时需要拆分方法或抽取子服务，参数过多时封装为 DTO 对象。

60. 禁止重复造轮子：日期处理（格式化、解析、计算间隔）、文件操作（读写、复制、压缩）、加密解密（MD5、AES、RSA）、集合操作、JSON 序列化反序列化统一使用 Hutool 工具库。Excel 导入导出统一使用 EasyExcel 框架。报表生成统一使用 JimuReport 引擎。

61. 利用 JDK 17 的新特性简化代码：DTO 和 VO 优先考虑使用 Record 类型代替传统的 POJO 类，减少样板代码。使用文本块简化多行 SQL 或 JSON 字符串的书写。使用模式匹配和密封类增强类型安全性。

62. 代码提交前必须清理未使用的 import 语句、未使用的局部变量、未被调用的私有方法、被注释掉的无用代码段。禁止空 catch 块存在，每个 catch 块至少要做日志记录。

## 数据库设计

63. 所有业务数据表必须包含四个基础字段：id（自增主键或雪花 ID）、create_time（创建时间，使用 MyBatis-Plus 的自动填充功能在插入时自动赋值）、update_time（更新时间，同样自动填充在插入和更新时赋值）、is_deleted（逻辑删除标记，0 为未删除，1 为已删除）。

64. 统一使用逻辑删除，is_deleted 字段结合 MyBatis-Plus 的 @TableLogic 注解。查询时自动拼接 WHERE is_deleted = 0，删除操作自动转为 UPDATE is_deleted = 1。禁止写物理 DELETE 语句。

65. 数据库禁止使用外键约束，关联关系的数据完整性校验统一在 Service 层通过代码实现。外键约束会增加数据库耦合度、影响写入性能、使分库分表和线上 DDL 操作变得困难。

66. 禁止使用 MySQL 的 ENUM 类型字段，改用 TINYINT 类型存储状态码，配合常量类或枚举类做代码层面的值映射。ENUM 类型扩展需要 ALTER TABLE，运维风险高。

## 接口设计

67. 所有接口的返回值固定使用 Result 泛型封装体，三层结构：code 为整型状态码（200 表示成功，其他值表示异常），msg 为字符串提示信息，data 为泛型数据载体。禁止返回 void、裸 String、裸 Map、裸 List、裸 Entity 类型。

68. 分页查询接口的返回值固定使用 PageResult 泛型封装体，包含四个字段：total（总记录数，Long 类型）、pageNum（当前页码，Integer 类型）、pageSize（每页条数，Integer 类型）、list（当前页数据列表，List 泛型）。

69. 接口路径采用 RESTful 风格设计，版本号放在 URL 路径中，格式为 /api/v1/模块名/资源名/{id}。GET 请求用于查询，POST 用于新增，PUT 用于完整更新，PATCH 用于部分更新，DELETE 用于删除（实际执行逻辑删除）。

70. 对外接口的字段只允许新增、不允许修改已有字段的类型或含义、不允许删除字段。需要废弃的字段标注 @Deprecated 注解并在注释中说明替代字段是什么。接口变更必须做版本管理，破坏性变更走新版本路径 /api/v2/。

71. 数据库密码、Redis 密码、JWT 签名密钥、e签宝 AppKey 和 AppSecret、第三方服务密钥等所有敏感配置，必须通过环境变量或配置中心注入，禁止在 application.yml 或 application.properties 中直接写死明文值。

## WebSocket 规范

72. Spring WebSocket 连接建立前必须做认证校验，在握手拦截器中验证请求携带的 JWT Token 有效性，未认证的连接直接拒绝。禁止允许未登录用户建立 WebSocket 连接。

73. WebSocket 消息体必须定义统一的 JSON 格式，包含消息类型、业务数据、时间戳等字段。服务端向客户端推送消息时，必须做用户维度的校验，只推送给有权限查看该消息的用户，禁止做全量广播。

74. WebSocket 服务端需要实现心跳机制，定期发送 Ping 帧或心跳消息，客户端没有在规定时间内响应则主动断开连接释放资源。同时设置单用户最大连接数限制，防止异常情况下一个用户创建大量连接。

## JimuReport 规范

75. JimuReport 报表的数据源配置走环境变量，禁止在报表模板中写死数据库连接信息。报表查询参数必须做 SQL 注入防护，所有查询走 MyBatis-Plus 参数绑定。

76. 复杂报表或大数据量报表的生成必须异步执行，避免阻塞 HTTP 请求线程。生成完成后通过 WebSocket 推送或系统消息通知用户下载。

77. 报表的访问和导出必须做权限控制，不同角色的用户只能查看和导出自己有权限的数据范围。报表模板的上传和修改功能只开放给管理员角色。


# 四、产出约束

1. 每次输出完整的分层代码文件，包含：Controller 类、Service 接口、ServiceImpl 实现类、DTO 入参类、VO 返回类、常量类和错误码枚举。所有文件按目录结构组织清晰。

2. 代码中的关键位置必须添加注释说明：事务边界标注（为什么这个方法需要事务，涉及哪些表的联动）、缓存策略说明（缓存的 Key 是什么、过期时间多久、什么时机清除）、分布式锁和并发控制说明（锁的粒度、超时时间、降级策略）、复杂业务逻辑的处理流程。简单的 getter/setter、字段赋值、log.info 日志语句不需要注释。

3. 代码交付时附带额外说明：每个接口的入参字段含义和校验规则、缓存 Key 设计和过期时间、事务方法的生效范围和注意点、特殊业务场景的风险点（如并发冲突、数据一致性）。
